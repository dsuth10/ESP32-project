# Hermes and companion orchestration investigation

21 October 2026

## Recommendation

Keep the classroom application as the product and source of truth. Extend its small, explicit local orchestrator for classroom workflows, durable jobs, media assets and device management. Add Hermes as an optional reasoning/tool-runtime adapter behind a narrow capability-checked interface where its richer agent tools materially help. Do not make Hermes the owner of companion history, generated media, device configuration or update lifecycle.

This is conditional on what “assistant” means. For a teacher-facing writing, image and shortcut workflow with strong privacy and predictable recovery, local orchestration should own permissions, state and results. For an advanced maintainer who wants Hermes' broader search, coding, memory or multi-provider agent experience, an optional Hermes profile/API connection is useful. Full Hermes embedding or requiring its desktop/gateway for ordinary classroom use adds a second agent product, provider setup and privileged tool surface without removing the application's need to validate and safely apply operations.

The repository already has both an embedded prototype and an older Hermes receiver path; it does not yet have a Hermes adapter for the new desktop assistant, shared conversation identity, durable assistant jobs, a canonical media library, or runtime ESP32 management. Avoid migrating accepted assistant/history work into Hermes sessions. The desktop SQLite remains canonical for companion requests and responses; Hermes `state.db` remains canonical for Hermes sessions and tool traces. Link the two with opaque IDs and user-selected context rather than mirroring or silently merging transcript stores.

## What exists in this checkout

- `tools/compose/assistant_service.py` implements a local Groq/Ollama chat loop. Ask exposes no tools. Manage has only status, explicitly enabled history search and save-text operations, with bounded prompts/turns/tool rounds, argument validation, same-request write deduplication and cancellation checks. The Ollama URL uses an OpenAI-shaped endpoint, but tool calling depends on the selected model/server implementing it; the code does not establish a generic compatible-server guarantee.
- `tools/compose/history_store.py` owns the companion's text-only SQLite store in the Windows app-data directory. `compose_gui.py` integrates it with the assistant and history panel. The first-increment note describes history retention, opt-out, copy/queue/export/delete and that an already-issued provider request cannot be recalled; an operation completed before cancellation is not undone.
- `server/hermes_voice_receiver.py` is a separate audio receiver for the ESP32. It transcribes audio and routes to configured Hermes Gateway sessions or Ollama/Groq paths. It holds a separate voice-session ID/config, and calls `/api/sessions/{id}/chat`; the Wi-Fi receiver's `/health` only shows liveness. `tools/compose/receiver_service.py` manages the optional host process, while the recent desktop integration can start it. This is not the desktop assistant's tool backend or conversation store.
- Device UI and shortcut definitions are still firmware constants. No runtime profile schema, authenticated configuration transport, capability negotiation or revision acknowledgement was found in the reviewed application/firmware sources. Device administration must therefore remain unavailable in assistant tools until that protocol exists.
- Media generation, editing, retrieval/import, asset revisioning and insertion into the companion's canonical library are absent from the reviewed desktop tools. Saving text is not a media asset workflow.

## What Hermes offers, and the boundary it leaves

Hermes Agent is MIT-licensed in its upstream repository; retain the copyright and licence notice for copied or redistributed portions. That licence does not cover separate models, credentials, hosted services or third-party libraries. The current documentation lists native Windows 10/11 installation and an MSIX desktop route (MSIX requires Windows 11 22H2+). Windows support is real, but should be checked against school-managed policies, machine architecture, optional dependency support and the deployment method, not assumed from upstream support alone. [Upstream repository](https://github.com/NousResearch/hermes-agent), [licence](https://github.com/NousResearch/hermes-agent/blob/main/LICENSE), [platform support](https://hermes-agent.nousresearch.com/docs/getting-started/platform-support), [Windows guide](https://hermes-agent.nousresearch.com/docs/user-guide/windows-native)

Hermes documents an OpenAI-compatible API server, authenticated with a bearer key, with chat completions and Responses, streaming, runs, stop/cancel, sessions endpoints, and `/v1/capabilities`, `/v1/toolsets` and `/v1/skills`. A run ID plus the documented `Idempotency-Key` can make supported run submissions safely retryable. The session REST endpoints provide a better adapter candidate than assuming generic `/v1/chat/completions` has session continuity. Pin and detect API capabilities at startup: these surfaces evolve, so do not rely on private Python imports or an unversioned, guessed endpoint.

“OpenAI-compatible” describes request/response shapes, not equivalent tools. Hermes' API server can invoke the configured agent toolset, including terminal and file operations. Groq/Ollama compatibility says nothing about Hermes skills, image generation, persistent sessions, cancellation, or tool safety. Enumerate and restrict actual Hermes toolsets; do not connect an unrestricted server to a teacher-facing device administrator. An app-side adapter should send only the selected request and requested context, never the full local history by default.

Hermes stores full agent sessions/messages in its own SQLite `~/.hermes/state.db`; curated memory is separate in `~/.hermes/memories/MEMORY.md` and `USER.md`. Its session search reads actual prior messages. The companion store instead contains its request/response and saved-text records. A user-selected “continue with Hermes” operation can provide a bounded excerpt or explicit session import, with visible destination/provider, and retain a mapping record. Do not treat Hermes memory as classroom history, or desktop SQLite as Hermes memory. Both are retained personal data and need separate clear/export/retention controls.

Hermes' image-generation feature supports generation and, for compatible backends/models, image editing. Its docs describe temporary provider URLs that Hermes materialises into a local cache; this is useful agent output handling, not a canonical asset library with stable identity, provenance, approvals, immutable versions and undoable insertion. Its image tools may depend on paid credentials or a Nous Portal subscription. The UI should show the exact backend and data destination before the request; no paid inference is assumed in this investigation. The companion still needs an app-owned asset operation that copies generated/imported bytes into managed storage, computes a content hash, records prompt/source/backend/license/parent version, produces a thumbnail, and returns a stable asset ID. The app must distinguish edits (new child version, never overwrite) from generated alternatives, and insert by stable ID into an explicit document/device target. Retrieval from filesystem, web or teacher-selected sources needs provenance and permission checks. [Image generation](https://hermes-agent.nousresearch.com/docs/user-guide/features/image-generation), [tool gateway](https://hermes-agent.nousresearch.com/docs/user-guide/features/tool-gateway)

## Product boundary and job design

Use providers behind `TextModel`, `AgentRuntime` and `MediaProvider` adapters; expose business operations through app-owned narrow tools. An optional Hermes adapter should implement submit/stream/status/cancel/session metadata and capability discovery, while the application owns policy, UI, local persistence and the final operation. Avoid “Hermes may run shell commands to configure the device”; give it a typed request such as `propose_profile_revision` whose payload is schema-validated and staged by the app. Initially, admin mode can produce a preview/revision for the user to apply; once a real authenticated transport is built, routine reversible label/shortcut changes may apply with clear undo and an acknowledgement.

Persist each long task before dispatch with an opaque request ID, scope, provider, state, progress, result IDs and audit receipt. Suggested states: `queued → running → awaiting_user → applying → succeeded`, with terminal `failed`, `cancelled` and `needs_recovery`. On restart, reconcile against provider run IDs and device revision acknowledgements; never infer success from a lost HTTP response. Use idempotency keys for remote submissions and local unique operation IDs for saves/inserts. For device changes, use optimistic expected revisions, validate capability/limits, retain the last-known-good revision and require device acknowledgement; apply/reconnect/reboot verification is distinct from successful transport. Retry read-only status/search automatically with bounds; retry writes only when the same idempotency key is guaranteed. For cancellation, stop future tool calls, send a provider stop when supported, fence stale callbacks with the request ID and report already-completed effects. Preserve completed receipts and require compensating undo for an applied setting rather than pretending cancellation rolled it back.

Privilege should be tiered: Ask gets no management tools; media gets only explicit asset operations; device management gets status and typed profile operations; maintainer development is a separate, isolated workflow with review/build/rollback. Treat prompts, retrieved media, history and tool output as untrusted data. Keep API keys in OS-protected storage, log identifiers/outcomes rather than prompts or transcripts, and do not retain raw classroom audio by default.

## Supportability, licensing and staged path

An external Hermes dependency means installation/version ownership, gateway start/stop, bearer-key storage, provider/model and skill setup, migrations/backups for two databases, diagnostics, offline fallback, and an upstream-change policy. Keep Hermes optional and report “not installed / unavailable / unsupported capability” without blocking existing Compose/Dictate or the local bounded assistant. Define a tested version range and contract fixture for any API adapter; never silently downgrade to chat completions if the requested tool/session semantics are missing.

1. Preserve the existing desktop assistant and History as they are; document the distinct receiver voice session and gateway session stores. Continue with the app-owned tool boundary and durable job/result schema.
2. Add canonical asset records and filesystem storage with version lineage, provenance, delete/export/backup, then generation/edit/retrieval adapters that save results before showing/inserting them.
3. Build the device capability/profile protocol and recovery path independently of an LLM. Add only typed, audited application operations after hardware ACK/reconnect behaviour is defined.
4. Prototype Hermes as an optional adapter. Verify capabilities/auth, stream reconnect, cancellation, idempotent retry and session identity against a pinned installed version. Restrict its toolset to the needed features and test offline/unavailable behaviour. Compare this with the current Groq/Ollama tool loop on the actual bounded classroom tasks.
5. Decide later whether a distinct maintainer mode benefits from Hermes coding tools. It must use an isolated checkout/build worker, explicit source permissions and artifact review; it must not inherit teacher device tools.

## Read-only runtime observation

The restricted agent sandbox could not reach loopback ports 8642 or 8787. A separate unrestricted host-level, read-only check then confirmed that both local TCP endpoints accept connections and return HTTP 200 from `/health`: Hermes API/gateway liveness on 8642 and the companion voice receiver on 8787. This is unauthenticated liveness only; it does not verify an authenticated Hermes session/tool operation, provider readiness, audio processing, ESP32 reachability, or every remote route. No process-name conclusion is drawn. No credentials, conversation content, transcripts or diagnostic logs were read. No services, firmware or inference providers were changed or invoked.
