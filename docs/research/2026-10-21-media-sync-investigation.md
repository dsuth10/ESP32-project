# Media library sync investigation

21 October 2026

## User direction and open decisions

The initial pilot should support OneNote and Word, with PowerPoint next. The library should default to both “prep” (prepare and manage an asset without a target open) and “live” (insert into the currently targeted application). Previously retrieved assets may be inserted automatically only when the target is unchanged; generated assets must be previewed first. Web retrieval is library-first and only occurs when explicitly requested. The pilot budget ceiling is A$30 per month.

Automatic home/work sync is required from the start. Two choices remain open: personal cloud vs home server vs school account, and whether the synced scope is media-only or includes History. The target-app order does not settle those account, privacy or synchronisation decisions.

## Sync mechanism options

**An ordinary synced folder** is the quickest path to synchronise immutable binary objects, but it is not an application database service. Each installation should keep its own SQLite database on local storage. SQLite’s own guidance warns against placing a database file on a network filesystem for multiple machines; WAL specifically requires clients to share memory and is unsupported across machines. A file-sync client introduces another layer that may observe a database, WAL or SHM file mid-transaction. Therefore do not sync or open the live `companion.sqlite3`, its sidecars, or a mutable manifest as a shared database. [SQLite: SQLite Over a Network](https://www.sqlite.org/useovernet.html), [SQLite WAL](https://www.sqlite.org/wal.html).

For a folder-based provider, use the provider’s desktop sync client to move **immutable, content-addressed media blobs** plus small immutable event/manifest files. A local coordinator publishes only fully written and hash-verified files by atomic rename; it never edits a blob in place. On other devices, a file watcher can signal new work, but correctness comes from scanning and verifying manifests/hashes after restart, not relying on notifications alone. Both users can add assets offline. Canonical changes are events with stable IDs and parent version IDs; if two devices concurrently nominate different canonical versions, preserve both and create an explicit conflict requiring resolution. Do not use last-writer-wins on titles, approval or canonical pointers.

OneDrive Files On-Demand can expose a file in Explorer while its bytes remain online-only; Microsoft says it must be pinned/downloaded for offline availability. That means an asset visible in a folder is not necessarily ready for offline insertion. The companion must detect hydration/availability or verify a local read and hash before showing “ready offline”. Managed organisations can also control Files On-Demand and sync policies. [Microsoft Files On-Demand](https://learn.microsoft.com/en-us/onedrive/files-on-demand-windows), [OneDrive sync planning](https://learn.microsoft.com/en-us/sharepoint/plan-file-sync).

**A provider API** gives the app explicit transfer state and stable provider item IDs, at the cost of OAuth implementation, token lifecycle, scopes, provider outages and account-policy dependencies. Microsoft Graph delta queries can resume discovery from a token, but return current item state rather than a full event history; the app must retain its own append-only event log. Graph upload sessions support resumable ranges and conflict behavior, useful for large media. Google Drive provides a changes feed and blob downloads; push notifications merely say changes are available and require an HTTPS webhook, so a desktop-only pilot can poll the change feed instead of operating a public webhook. [Graph driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0), [Graph upload session](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0), [Google Drive changes](https://developers.google.com/workspace/drive/api/guides/manage-changes), [Google Drive downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads).

**A home server** can be a self-hosted file endpoint or a proper client/server service. A file endpoint has similar mutable-file and conflict hazards to a synced folder; it should only receive immutable objects and event records. A service with an API, database (for example PostgreSQL), per-device authentication, append-only events, conditional writes and blob storage is the stronger multi-writer design, but it creates a home internet/server dependency, backup and patching work, and availability/support burden. Home-server sync must be designed for work networks where inbound access may be blocked; client-initiated outbound sync or a VPN is safer than exposing an unauthenticated file share. This is an option to evaluate, not a claim of zero cost or guaranteed access.

## Proposed data and conflict model

Keep one local SQLite database per computer under that user’s app-data directory, and store local blobs by SHA-256 hash. Sync immutable media bytes and immutable metadata/event records; never sync the SQLite database, credentials, temporary previews, caches or raw audio by default. Each device maintains a local outbox with event UUID, device ID, monotonic device sequence, event type, asset/version IDs, parent/base version, timestamp, content hash and sync state. Acknowledged event IDs and provider cursors let retries be idempotent. Use exponential backoff for transient failures, bounded retries for permanent failures, and visible “local only / syncing / synced / conflict / unavailable” states.

An event log supports offline merge; it does not make competing canonical choices safe to merge automatically. Asset bytes are immutable, so identical hashes deduplicate; versions with different hashes remain separate. Treat canonical version, approval, deletion and rights review as conflict-sensitive state. Use tombstones for deletion so offline devices eventually learn it, and do not garbage-collect a blob while any asset version, derived version, pending event, insertion receipt or retained backup references it. Store per-object reference counts as a derived/rebuildable index, not the sole source of truth. Verify hash and byte length after upload and download; quarantine mismatches. A manifest becomes visible only after all referenced blobs are available remotely.

For an A$30 monthly ceiling, the pilot should record actual API/provider/storage charges and warn before the ceiling, with generation/search separately gated. A local sync utility or provider plan must not be described as free or included without checking the selected plan, storage quota, API pricing, tax, and any home-server costs. Cost and storage limits depend on the user’s provider and media volume.

## Credential and content boundary

Keep OAuth tokens or server credentials in Windows-protected credential storage, never in SQLite events, the media directory, filenames or firmware. Request minimum scopes: access only the app’s chosen library location where provider APIs support it, and do not request mailbox or broad drive access to make sync convenient. A school account may have tenant-admin consent, external-sharing, data-loss prevention and retention rules; the app must expose an account-policy failure instead of silently switching accounts. Personal cloud sync avoids some school tenancy dependencies but moves classroom-created media and metadata to a personal account, which may be disallowed.

“Media-only” still syncs potentially sensitive filenames, titles, descriptions, alt text, tags, prompts, source URLs, rights notes, timestamps and insertion records. “History included” can expose spoken requests, generated responses and possibly school/student context across personal and work computers. Keep prompts and chat History local unless explicitly selected; if cross-device retrieval is required, design a separate opt-in scope with retention, delete, encryption and account-boundary controls. The user must choose whether sync covers binary assets and provenance only, or also History/events that may reveal content. Syncing local files is not end-to-end encryption unless the chosen provider/service and application implement and verify that property.

## Recommended gate

Build the local library and append-only event model first, with sync behind a provider interface. For the initial two-device trial, require always-local ready-to-insert copies for approved canonical images and make network sync status explicit. Do not use online-only placeholders for a live insertion. Prove interrupted upload/download recovery, duplicate-event suppression, hash mismatch handling, simultaneous offline edits, canonical conflict resolution, deletion tombstones, credential revocation, school-network restrictions and backup/restore using synthetic media.

At the time this initial investigation was drafted, provider and synced-content scope remained undecided. The later section records the subsequent choice of a private Linux host alongside Hermes, preferably reached through Tailscale. The user subsequently confirmed media and its metadata only; conversation History, prompts, credentials and device/network settings stay local. School policy and tailnet access on work devices still need verification.


## User-selected hosting direction: private Linux cloud on the Hermes machine

The selected home is a private cloud hosted on the existing Linux computer where Hermes runs, reachable on the current network and preferably through Tailscale. The supported product model should treat it as a stable service host and each Windows computer as an independently usable client with its own SQLite database, local cache and pending sync outbox. “On the same network” is a useful fast path, while the stable server identity is what lets a laptop continue to find the same library when it moves between home and work. A changing home LAN address alone is not a durable identity. The server should have a stable local DNS/DHCP reservation for local access and a stable tailnet device name/identity for remote access, if Tailscale is available on both endpoints. This does not establish that the school network allows tailnet traffic or that the user’s Tailscale account/device setup is already ready.

Run a small authenticated media/metadata API beside Hermes, bound to loopback or the intended private interface; keep its storage directory and database on the Linux host’s local filesystem. The API owns all server-side reads/writes and transaction boundaries. SQLite is suitable for a single host when only that API process accesses the database; desktop clients must call the API and must never mount or open the server’s SQLite file, WAL, or SHM files. If concurrent service processes or larger multi-user load later require it, a server database is an architectural migration, not a reason to share the SQLite file over SMB/NFS. Keep Hermes model/runtime data, credentials and logs in separate directories and service permissions from the media library. Store immutable media blobs by content hash; store version/provenance metadata, event IDs, device cursors and conflict state in the API’s database. Authenticate every request, authorise the account/device, and recheck server-side hash and size limits. Desktop clients keep local usable copies of approved insertable assets and queue immutable upload/download events while offline; sync resumes and deduplicates by stable event ID and hash. A sync ACK means the server committed the blob and metadata, not that a Word/OneNote insertion was accepted.

Tailscale is a private network layer, not the library API’s complete authentication or authorisation layer. Tailscale Serve can proxy a local service to devices in the same tailnet, supports HTTPS on the tailnet DNS name, and remains subject to access-control rules. Its documentation contrasts this with Funnel, which exposes a service to the public internet. For this classroom library, use Serve/private tailnet routing only if configured and verified; do not configure Funnel, public port forwarding or an unauthenticated file share. Explicitly grant only the owner’s intended Windows clients access to the Linux host and required API port. Then have the API authenticate the app/user and enforce per-operation permissions too. Do not assume Tailscale SSH is enabled or needed: library sync should use the API over HTTPS, not shell access. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve), [Tailscale access control](https://tailscale.com/docs/features/access-control), [Tailscale grants](https://tailscale.com/docs/features/access-control/grants), [Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel).

Home-server availability is a real dependency: when the Linux host is asleep, shut down, offline or unreachable from work, clients retain their local library and queue changes, but cannot retrieve a missing blob or claim the server has accepted an upload. On a school network, Tailscale may be blocked or unavailable under school device/network policy; the client should report that and keep local work available, not fall back to public internet exposure. Validate local-network and tailnet routes separately, including HTTPS certificate/name validation, host reboot, Hermes restart, Windows sleep/wake, school-network access when permitted, account revocation, interrupted transfers, duplicate/out-of-order events and simultaneous offline canonical edits. Test with synthetic media and confirm the home server’s backup/restore before storing classroom content.

The user subsequently confirmed that sync covers media and its metadata only, excluding conversation History, generation prompts, credentials and device/network settings. Work-device and content permission to use the personal tailnet/home host still needs verification. Personal hosting makes data control local to the user, but the metadata and classroom media are still sensitive personal/work content. Confirm the applicable school policy before syncing student-identifiable material or History. Do not route library prompts or media through Hermes merely because both services run on the same machine; generation, sync and storage should remain separate operations with explicit provider/budget controls.
