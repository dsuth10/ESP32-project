This evidence note was drafted before the requirements interview concluded. The confirmed destination, automatic sync and insertion choices in [the master plan](../2026-10-21-companion-media-agent-master-plan.md) supersede its provisional workflow recommendations.

## Scope and current baseline

This is a planning investigation for a future media-library increment. It does not implement media storage, generation, web search, OneNote or Word support, or any target-app adapter. The companion’s first working increment has a local SQLite History for request/response text, saved text and deliberate Paste Ready queueing. `HistoryStore` schema v1 stores mode, request, response, provider, status, timestamp, title and saved flag; its search covers those text fields. There is no media asset record or binary store in this schema. The Windows `ClipboardManager` reads/writes Unicode text and sends Ctrl+V. `FocusTracker` records foreground HWND, title, PID and UIA runtime ID, and can check whether that target still has focus. This is valuable for safe deferred delivery, but does not identify a caret, insertion point semantics, target document, selection replacement behaviour or app-specific media support.

The approved direction remains conditional. The first-increment document says retained text can be queued to Paste Ready; it does not approve a OneNote or Word destination. A destination must be chosen and tested before a support claim is made. Use “candidate adapter” until that happens.

## Recommended product flow

A spoken request such as “make a labelled diagram of the water cycle and put it in my notes” should become a durable, user-visible job:

1. **Capture and resolve.** Transcribe the request, identify asset type, audience, dimensions/aspect ratio, language, intended use and destination if supplied. Ask only for missing information that changes the output or insertion target. Present the resolved brief before any paid generation or external search. A request to “use the picture we made last week” should search the user’s asset library first.
2. **Acquire.** Offer provenance choices: user-owned/imported file, existing library asset, or web search for a reusable/licensed source. For an imported file, retain original bytes and record supplied ownership/source details. For web assets, record source URL, creator/rights statement, retrieval time, licence evidence and attribution requirements; do not treat search-result visibility as permission. For generated media, record provider/model, prompt, job/request ID where available, generation time, cost/usage receipt and original output. Never make an automatic paid retry after an uncertain timeout. Show the prior job state and offer a deliberate retry that creates a linked new attempt.
3. **Refine and approve.** Keep every approved rendition immutable. Editing, cropping, resizing, audio mastering, video transcoding or changing embedded text creates a derived version with parent hash, operation/tool/version and parameters. Show a preview and metadata (including source/licence and generation cost where applicable); teacher approval selects a canonical version for the particular use. A later edit never silently replaces the approved canonical version. Reject unsafe/unsupported formats and enforce size/duration limits before creating derivatives.
4. **Prepare and insert.** Resolve the target again immediately before insertion. Queue an intent containing asset/version ID, target window/control snapshot, requested operation (for example insert at caret, add attachment, or set slide media), and expiry. On user action, verify target identity and focus; if it has changed, stop and ask the user to reselect/requeue. A clear ready state should say which asset and which operation are queued. The adapter should report whether it accepted the command and what it can verify; retain the asset and intent on failure.
5. **Verify and record lineage.** Distinguish “copied to clipboard”, “adapter call returned”, “object appeared in target”, “saved/reopened successfully” and “teacher accepted it”. The first two are transport evidence, not proof of embedded document content. Save an insertion receipt with asset version/hash, adapter/version, target app/version, document/page/slide reference where available, timestamp, outcome and verification level. A later query such as “find the water cycle diagram I used last term” should search both library metadata and insertion receipts, then offer preview/open/copy/reinsert. Reinsertion is a new intent and requires a fresh target check.

## Proposed data model and storage

Keep SQLite as the index and use a separate application-owned asset directory under the companion’s user data root for binary objects. Do not place classroom media in the ESP32 or firmware: the handheld is a trigger/controller, can be disconnected, has limited storage, and is not the authoritative library. The device should receive no media bytes unless a distinct device feature and capacity are explicitly designed.

Suggested entities:

- **Asset**: stable UUID, media kind/MIME, title, description, accessibility text/caption, language, tags, created time, lifecycle state and canonical version ID.
- **AssetVersion**: immutable version UUID, SHA-256 content hash, byte length, detected MIME, dimensions/duration, relative managed path, parent version, transformation record, created time and approval state.
- **Provenance**: source kind (user import, generated, web, derived), original filename/source URL, creator/provider/model, prompt or generation brief, job ID, retrieval/generation time, rights/licence text and evidence URL, attribution, cost/usage receipt and user attestation. Keep prompts and school/student content under the same privacy controls as History; avoid storing secrets.
- **InsertionIntent / Receipt**: asset version, requested operation, target snapshot/app adapter, queue/expiry, result and verification level. Do not store full document text by default.
- **GenerationAttempt**: idempotency key, request fingerprint, provider job identifier/status, cost estimate/receipt and retry relationship. A repeated UI event for the same pending attempt must resume/status-check rather than create a second billable request.

Use content hash for integrity and exact-byte deduplication, while retaining separate asset identities where provenance/use differ. Hashes do not prove authorship, licence or safety. Store blobs atomically (temporary write, flush, verify hash, rename) before committing their index row; reconcile orphan files/index rows on startup. Back up the database and asset tree together, and test restore. Deleting an asset must account for derived children, receipts and backup retention; provide explicit delete/export controls and no hidden indefinite retention.

The clipboard can carry multiple formats for one operation. Microsoft documents that targets retrieve the most descriptive format they recognise and that Windows can synthesise conversions. For still-image interoperability, Microsoft recommends CF_DIB or CF_DIBV5 rather than device-dependent CF_BITMAP. CF_HDROP carries fully qualified paths to existing files; therefore placing a file path on the clipboard offers a file-drop representation, not proof that the application embedded the file’s bytes. Clipboard adapters should set formats appropriate to the selected operation, preserve/restore prior clipboard data as far as feasible, and disclose that other software may observe clipboard contents. See [Microsoft clipboard formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats) and [Shell CF_HDROP format](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard).

## Candidate insertion support matrix

Proof levels: **P0** design/source documentation only; **P1** adapter command accepted; **P2** target object visibly present; **P3** save, close/reopen and verify; **P4** teacher accepts it in the intended classroom workflow. No destination currently has P2–P4 evidence in this investigation.

|---|---|---|---|
| Generic clipboard | CF_DIB/V5 is a reasonable candidate image payload where target recognises it. | No generic portable embed representation established here. | P0. Ctrl+V acceptance and image representation vary by app; never claim document persistence from clipboard write. |
| Word desktop candidate | Microsoft Word VBA `InlineShapes.AddPicture(FileName, LinkToFile, SaveWithDocument, Range)` supports a file path, independent copy vs link, save-with-document and explicit range. This is a stronger insertion adapter candidate than blind paste. | Requires separate Word object-model research and testing before promising media insertion. | P0 from API documentation; test approved Word version, caret/selection, undo, save/reopen, protected view and school policy. | PowerPoint desktop candidate | `Shapes.AddPicture` exists in the object model; verify the exact method/parameters and behaviour before implementation. | `Shapes.AddMediaObject2` adds audio/video with explicit file path, link/embed flags and slide geometry; at least one of LinkToFile or SaveWithDocument must be True. | P0. Verify embed vs link, supported codecs, playback after moving source file, save/reopen and slide position. Requires account consent, network, permissions and correct page selection; it cannot establish the active desktop caret. Browser-based rich editors may expose their own paste/upload/editor API. | Editor-specific upload/embed behaviour only. | P0. No cross-browser document adapter should be claimed. For OneNote Graph, Microsoft states image updates require image data in the request or a multipart part, rather than the service downloading arbitrary www links; this makes provenance retrieval and page mutation distinct steps. Its API supports page HTML and resource attachments, but is not a Windows focused-control/caret protocol. Graph and desktop OneNote are distinct adapters with separate identity, permission, sync and verification requirements. The documented route is a capability signal, not approval to use either route.

## Security, privacy and school deployment

Treat user speech, imported files, generated output, web pages, OCR, metadata and tool results as untrusted content. They may contain instructions, personal information, copyrighted material, malware or misleading licence claims. Parsing or previewing media must not execute active content; use safe decoders, bounded resource use, file type detection, malware scanning where available, and temporary isolated preview paths. Strip location/device metadata from public derivatives when appropriate, retaining original provenance privately if required.

Keep image/audio/video bytes out of model context unless the user explicitly asks for analysis and the selected provider/policy allows it. Explain when an image, prompt, transcript or search request leaves the device for cloud generation/search. Respect LOCAL_ONLY and school network policy; local reasoning does not make external retrieval local. Do not include student names, faces, voices or work in a prompt by default. Offer a no-retention mode and clear deletion/export; school-managed deployment should define approved providers, retention, backup, licence review and who can access the per-user asset directory. Do not quietly upload the library for sync or backup.

## Acceptance plan once a destination is selected

Use synthetic, non-student material first. Verify: import preserves source/hash; duplicate bytes do not create duplicate storage; derived edits retain parent lineage; an approved version stays stable; a simulated generation timeout does not call the paid provider twice; search retrieves by title/tag/source and insertion receipt; corrupt/missing blobs fail safely; delete/export and backup restore behave as stated. Then use the chosen target app to test image insertion at caret and over a selection, focus changes while queued, app minimisation, elevated target boundary, clipboard interference, undo, save/reopen, sync/offline and duplicate-insert prevention. For audio/video, add playback, codec, duration/size, link-vs-embed and moved/deleted source tests. Have the teacher confirm actual usability before describing the capability as accepted.

The first releasable slice should be a local library with import, metadata/provenance, preview, immutable versions, search and an image-only insertion adapter for one explicitly chosen desktop app. Keep generation, web retrieval and audio/video insertion behind later gates until their cost/licensing and target-app acceptance are demonstrated.
