# Adoption and onboarding research: ESP32 classroom presentation companion

> Historical design, investigation or checkpoint evidence. Current scope/status is governed by the [consolidated branch programme](../2026-10-21-companion-media-agent-master-plan.md): original S3 only, CYD application port abandoned, Groq primary and the same Linux Hermes over permanent private Tailscale required at home/work. Earlier proposals and test observations below are not proof of current deployment or release acceptance.

Date: 21 October 2026

## Scope and evidence boundary

This note assesses practical distribution for the current ES3C28P ESP32-S3 classroom companion, its Windows Compose and Dictate utility, and the optional Wi-Fi voice receiver. Repository facts below come from the checked-in README, `platformio.ini`, `src/wifi_config.h.example`, `tools/compose/start_compose.bat`, `tools/compose/compose.env.example`, and the host receiver and companion source. Recommendations are proposals, not implemented behaviour. External claims use official project, vendor, or platform documentation.

## What a teacher can do today

The hardware and features are concrete: the repo targets the LCDWIKI / QD Electronic ES3C28P ESP32-S3 touchscreen board. A teacher can pair its BLE keyboard profile, use Bluetooth shortcuts, start the Windows Compose companion, and use the PC microphone for speech-to-text or writing. Optional device-recorded voice travels over Wi-Fi to a host receiver on TCP 8787, with UDP 8788 discovery; the receiver can use local Ollama and/or Hermes. The README already explains Home/Work profiles and recommends an IDE agent for development and physical testing.

The current path still assumes a technical installer. Firmware setup requires a PlatformIO build/upload, editing a local `wifi_config.h` and rebuilding for network credentials. Compose and Dictate requires Python and packages, a copied `compose.env`, and a user-launched batch file. The batch file searches for a project-local virtual environment or selected system Python versions. It does not run automatically at sign-in. Opening the companion GUI also starts the receiver service, so the current host experience couples PC-microphone Compose/Dictate with the Wi-Fi voice receiver's Python dependencies and port 8787. Cloud STT/LLM requires an API key; offline operation requires local Whisper/Ollama setup and models. These are reasonable maker steps but are not a no-code teacher setup.

## Firmware distribution and Wi-Fi setup

A browser flasher can remove the need for a teacher to install PlatformIO. ESP Web Tools is a browser component that installs prebuilt ESP firmware from a manifest, can optionally run Improv Wi-Fi configuration, and provides logs/terminal access. It requires a secure HTTPS page and a browser with Web Serial; the project documentation names Chrome and Edge as supported desktop choices. Espressif's own `esptool-js` is another browser Web Serial flasher, but its documentation explicitly says it does not build firmware images from ELF files. These are distribution/flashing tools, not a replacement for compiling and validating the firmware.

ESP Web Tools expects deployable prebuilt images. Its documentation says ESP-IDF v4+ ESP32 firmware needs to be merged to a single binary before use; the project uses Arduino via PlatformIO, so the exact PlatformIO output/merge recipe must be verified for this board and partition map. The repository uses a custom 16 MB board configuration, PSRAM, and custom partitions. A safe release should publish versioned, reproducibly built images plus checksums and a manifest, then validate flashing and first boot on a real ES3C28P board. Treat recovery and rollback as part of the install flow.

Improv is an open Wi-Fi provisioning protocol over either USB/UART serial or BLE. Improv Serial sends network credentials through a serial port. ESP Web Tools can use this protocol during browser setup. The current firmware does not implement Improv: network values are compile-time macros in `wifi_config.h.example`. Making Improv work therefore requires firmware work to accept and persist provisioned credentials, define a reset/reconfigure flow, and ensure that setup secrets do not appear in logs. Improv configures Wi-Fi; it does not automatically configure the receiver URL, authentication token, cloud credentials, or school firewall.

This board is an ESP32-S3. Espressif lists ESP32-S3 as Bluetooth LE-only; original ESP32 is dual-mode and supports Bluetooth Classic as well as BLE. The existing S3 BLE HID keyboard must remain BLE. Do not describe it as a Classic Bluetooth keyboard, and do not choose an onboarding method that assumes Classic Bluetooth. Improv BLE is technically a candidate if the firmware adds the GATT service and coexists with the existing HID service; validate this with Windows pairing and phone/browser provisioning before promising it. Serial over USB is an easier first firmware provisioning path where school policy permits the serial device and browser access.

Web Serial is a useful fallback for initial setup and support, but it depends on browser support, HTTPS, an available serial device and an explicit user port selection. Espressif says its browser flasher uses Chrome or Edge. School browser policy, USB device-install restrictions, and driver/interface availability can still block it. A school IT deployment path should therefore be available alongside the self-serve web installer.

## Windows school deployment

Plan for three independent Windows permissions:

1. **Running the companion.** A packaged desktop app may install per user, but school controls can prevent user app-package installs or block execution. Windows 11 SE is especially restrictive: Microsoft's Education guidance says users cannot install and use arbitrary third-party apps; IT must deploy supported apps through Intune and allowlist or managed-installer policy. A signed package and an Intune deployment option are more useful to schools than a Python setup guide alone. A self-extracting portable folder can reduce installation steps on unmanaged home PCs, but it is still executable software and can be blocked by WDAC/AppLocker.
2. **Bluetooth pairing and HID use.** The device uses BLE keyboard input for both shortcuts and Compose/Dictate hotkeys. Microsoft Intune exposes policies that can block Bluetooth or pre-pairing. If Bluetooth is disabled, restricted, or the device cannot be paired, the teacher needs an alternate keyboard shortcut path where feasible, or the school must approve pairing.
3. **Microphone, USB and network access.** Compose/Dictate records the Windows PC microphone, so Windows privacy settings and organisational policy can affect capture. Firmware upload / serial provisioning needs USB serial access; Microsoft documents machine-level device-installation restrictions and allow/deny rules. Optional device voice requires the ESP32 and receiver PC to reach each other on the local network. The current receiver's 8787/TCP and discovery 8788/UDP may be blocked by host firewall, client isolation, VLANs, or hotspot policy. Discovery is convenience only: document manual receiver configuration as a fallback. For a phone hotspot, verify client-to-client reachability on each target hotspot; a successful internet connection alone does not prove ESP32-to-PC access.

The teacher-facing setup should report these as explicit checks, not generic “connection failed”: app starts; microphone permission and selected device; BLE keyboard paired and connected; serial port visible (only for firmware setup); receiver health reachable; selected provider and whether it is local or cloud. Offer a “Save diagnostic report” button that omits API keys, Wi-Fi passwords, transcript/audio and clipboard contents by default. Include a copyable short result for school IT (device name, Windows/browser version, error category, requested ports and app publisher/version). Keep richer logs local, redact tokens, and make retention visible. The repo currently has logs and status information but they are not yet packaged as a teacher-friendly support report.

## Recommended onboarding shape

Separate the first successful use from optional AI configuration. A practical order is:

- **Quick-start path:** let the teacher use the companion's own buttons on a Windows PC before depending on the ESP32; then pair “ESP32 MacroPad” for remote shortcuts. Select the microphone and try a short Dictate test in a blank document. A signed, school-deployed companion could make this the first path. Decouple or make the receiver service optional so this test need not also configure port 8787. The path should not require the teacher to configure a Hermes server or obtain an API key. A bundled or wizard-installed local speech model is still necessary for the existing Whisper path; Compose and optional cleanup also need a configured text-generation backend.
- **Local writing path:** pre-package the companion, Whisper runtime/model, and a supported local text-generation endpoint only if local AI is a chosen supported installation. Give the teacher one clearly labelled “Local only” mode. Do not imply that “local” works until model availability, first-run download, disk use, microphone processing, and actual output have been checked on a school standard account.
- **Optional school/Home AI path:** add a setup screen for a compatible local or network endpoint. Test from a guest/hotspot network as well as the home LAN. Default to no remote voice transmission until a teacher explicitly selects a cloud provider and sees what is sent.
- **Maker path:** retain the full repo, PlatformIO, serial logs and IDE agent instructions for users who want to modify hardware or firmware. Make it clearly optional to ordinary classroom users.

A brief paper quick-start card should show icons and plain language rather than command lines. Use the physical device's screen for guided pairing, “hold to talk” instructions, Wi-Fi status, and an actionable failure code. Keep an offline/basic shortcut mode available even when all AI backends are unavailable.

## AI-agent-managed product pattern

The project can welcome AI coding agents without requiring a particular one in classroom use. Keep the public repo self-describing: a concise architecture page, an `AGENTS.md` with safety and hardware constraints, one documented build/flash command, a documented diagnostics command, versioned firmware outputs, and an issue template asking for board revision, firmware version, Windows version, exact action and redacted diagnostic ID. This makes the project discoverable to Codex, Cursor, Gemini, and local coding tools while retaining a human-readable path.

For maintainers, define a small provider/transport adapter boundary around speech recognition, text generation, and optional voice receiver calls. Keep the user-facing controls named by purpose (Local, School endpoint, Cloud provider) and surface “provider used” for each request. Offer conventional HTTP interfaces where possible: Hermes documents an OpenAI-compatible API server with session endpoints, but the current ESP32 voice receiver has Hermes-specific session calls and a Groq/Ollama pipeline in Compose. An adapter should perform startup capability checks, timeouts, and explicit data-flow reporting; it should not claim that every OpenAI-compatible API has Hermes tools or session semantics.

No formal universal agent-management API for this product was identified. MCP is useful as an optional maintainer/developer integration, not a prerequisite for device setup. First define a documented local diagnose, configure, restart, update and rollback interface, with a structured diagnostic report; then optional MCP adapters and concise agent instructions can call those stable operations. This lets a user invoke the same checks from a terminal, a school IT script or different agents without making the product depend on a single assistant vendor. Any agent action that flashes firmware, changes Wi-Fi, or sends audio should show the target and data destination and require a clear user action.

## Decision summary

The best near-term adoption improvement is a Windows companion that supports a PC-only Dictate test first, plus optional BLE remote pairing and clear school IT deployment instructions. Decoupling the current auto-started receiver will remove unrelated setup requirements from that first test. A browser-based, prebuilt firmware installer plus Improv Serial is a promising later step, but requires credential storage/provisioning in firmware and board-specific merged images. Keep Hermes and network voice advanced options until network, firewall, privacy, and credential behaviour have explicit setup checks. For AI-agent support, publish stable diagnostic and lifecycle commands first, then optional adapters for multiple compatible clients.
